Plain-English summary

What did we actually build?

Imagine you have several approved Jcode workspaces, like rooms in the same office. Before this change, Jcode could send a message to another room, but it did not have one simple noticeboard showing which rooms were available and what kind of recent exchanges happened.

Now you can type one command:

/peers

Jcode immediately shows a local overview. It tells you who “you” are in the peer group, confirms whether Ambient initiation is on or off, shows whether each approved peer is ready, busy, offline, or unclear, and lists up to five recent exchange outcomes. It does this without asking GPT, Claude, or any other AI model.

Why that matters: You get fast operational awareness without spending model tokens, exposing message contents, or accidentally starting work in another project.

How it works

A simple three-step flow

1You type /peers

Jcode recognizes a built-in command. No model prompt is created.

→
2The local server checks facts

It checks the exact approved workspace, live peer connections, and a small bounded slice of saved local history.

→
3Jcode draws a safe card

The screen receives only a sanitized summary and displays it inside the normal Jcode interface.

Why use existing transcripts?

Jcode already saves its own session history. The new overview reads a carefully limited portion of that existing history instead of creating a second database full of sensitive peer messages. This keeps the design simpler, reduces duplicate private data, and allows recent activity to survive a restart.

Why does the server own the answer?

The shared Jcode server knows which peer sessions are actually connected. Letting the server produce the overview prevents the screen from guessing. The new route is read-only and one-shot. It cannot be reused to send a message, wake a peer, or keep a hidden connection open.

Privacy and safety

What the feature is allowed to reveal

Allowed

Approved peer label, project label, simple availability state, direction of exchange, broad outcome, and relative time.

Hidden

Message bodies, error details, capability values, full paths, raw request IDs, raw session IDs, and unrelated workspace history.

Never triggered

No model call, no peer wake-up, no outbound message, no Ambient Mode change, and no new conversation turn.

Hard limits that prevent an unlimited history scan

LimitExact ruleReason
Saved sessionsAt most 12 matching sessionsStops the command from walking through an unlimited archive.
Total snapshotAt most 2 MiBKeeps memory and disk work predictable.
Messages per sessionNewest 500 onlyOld history cannot make the overview grow forever.
Displayed activitiesNewest 5 onlyThe card stays useful and readable.
Workspace matchingExact canonical workspaceHistory from similarly named or unrelated folders is excluded.
Honest limitation: If the saved history hits a safety limit, Jcode marks the history as limited rather than silently pretending the result is complete.

What went wrong, in simple terms

Software work is rarely a straight line. These issues were encountered and handled without hiding them.

The outside Claude review command failed

The local Claude command was first called with an invalid tool option and then failed again without useful output. This was a review-tool problem, not a feature failure. We stopped wasting time and tokens on it, then relied on direct code tests and runtime evidence.

One large test failed only during parallel execution

A restart snapshot test saw two live test sessions because other tests were changing the same process-wide test home at the same time. The test passed alone, all six related restart tests passed serially, and the full application suite then passed serially with 1,141 successes. No unrelated code was changed to disguise the interference.

The first full workspace compile hit the time limit

It was still compiling and showed no code error. We reran it after the compiler cache was warm, and it finished successfully.

The official self-development command could publish but not open a screen

The build ran in the background without an interactive terminal. Publishing succeeded, then the attempt to launch the visual interface failed because no terminal was attached. We verified the published executable directly and aligned the shared server using Jcode’s Windows-safe staged replacement method.

The first live terminal test typed too early

The Jcode screen was still changing sessions, so the first /peers input was lost. The harness was changed to wait for the stable branch and provider display. The second attempt passed every live check.

WSL could not be used for terminal testing

Windows Subsystem for Linux is present but has no Linux distribution installed. We did not install one or alter the machine. Instead, we used a temporary isolated Windows ConPTY environment and removed the need for WSL.
